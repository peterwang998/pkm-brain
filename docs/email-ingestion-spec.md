# Email Ingestion

**Status:** Gmail operational mirroring and the encrypted archive are implemented and live-validated; the opt-in projection-v7 Gmail Knowledge adapter, authoritative review-only temporal runner, and append-only review ledger are implemented and full-corpus structurally validated in an isolated Brain v2 home, but private semantic gold, original-Brain parity, and the canary still block production promotion
**Last verified:** 2026-07-23 against 7,125 locally rebuilt projection-v7/classifier-v5 revisions, 6,960 active documents, 165 deleted revisions, 7,859 active-message ranges, and the sealed 12-case public-synthetic V4 temporal replay

The owner-authorized operational lane uses exact-scope `gmail.readonly` API access to maintain a bounded, rebuildable local mirror at `~/brain/cache/gmail-mirror/gmail-mirror.sqlite`: exact seven-day bootstrap, history-based incremental sync about every 600 seconds, immutable sanitized revisions/current pointers, provider-confirmed tombstones, a durable triage queue, content-free poison-thread quarantine, recoverable saved page tokens, and one atomic provider checkpoint. After normal checkpoint acceptance, at most ten due quarantined threads may be retried in a second generation with durable exponential backoff and parser-version reprocessing; retry-only failure cannot make an accepted mailbox checkpoint stale. Attachment metadata may be retained, but attachment bodies/bytes are not fetched or stored. Luna drains the local queue with no Gmail calls, and mailbox freshness plus scheduled-sync health remain independent from analysis/quarantine backlog.

This mirror remains operational evidence only. It does not itself create inbox artifacts, documents, chunks, facts, entities, retrieval indexes, or wiki pages. The separate, explicitly enabled Gmail Knowledge projection below reads the encrypted archive locally after provider sync; neither operational store depends on Knowledge health.

## Gmail Knowledge Projection

The Gmail connector is opt-in and disabled by default. Once explicitly enabled, it reads the already-approved encrypted archive locally and creates one immutable `gmail_thread` Markdown revision for each changed visible thread. It never calls Gmail, mutates the mailbox, reads attachment bodies into Knowledge, or exports mail through the Brain sync outbox. A bounded scheduled job runs about every 600 seconds independently of provider synchronization; initial backfill can explicitly select an unbounded local batch.

Each revision preserves the Gmail account/thread/message lineage, provider internal message times, archive revision, subject and address metadata, bounded attachment descriptors, and bounded text bodies. Quoted reply history is stripped and the newest retained correspondence wins when a thread exceeds the body cap. Normalized message text is plaintext by design, so the target Brain home is changed to owner-only directories and databases before capture; captured and raw revision files are mode `0600`.

Revisions are immutable. Archive schema v2 derives the provider revision from stable raw-content and canonical metadata/label digests, so a same-size update within the same provider-clock second still changes revision while label ordering and clean rebuild clocks do not. Legacy rows receive one idempotent digest backfill. The Knowledge projection identity includes the full account, thread, provider revision, and explicit renderer/classifier versions. A semantic normalization change therefore creates exactly one new projection even when Gmail itself has not changed. Gmail documents use the stable `gmail-knowledge` ingest origin rather than a machine hostname, and a matching legacy path is migrated without duplication. After indexing, only the newest non-deleted projection of a thread remains active in FTS/vector retrieval and fact extraction. Older documents and chunks are retained in SQLite but marked `superseded` and removed from retrieval indexes, preserving evidence cited by facts. A provider deletion creates a tombstone revision and retires the previous active revision without erasing its evidence.

Capture validates both the inbox projection and copied raw artifact. A corrupt raw copy may be atomically repaired only from an inbox artifact whose content hash and Gmail lineage validate; otherwise the revision remains inactive. If reconciliation reactivates a retained fallback, it restores the existing chunk IDs into FTS and vectors before marking the document active. Failed restoration holds the document superseded and makes the run partial. Capture, ingest, vector-write, and reconciliation errors propagate to the scheduled-run result; a failed preflight or capture with no output cannot reconcile stale files. Provider lineage in error paths is reduced to an opaque correlation hash plus local exception class.

All active normalized Gmail revisions are indexed for explicit mail recall. Generic Brain retrieval suppresses bulk/advertising mail plus routine `transactional` and `unknown` mail unless the query explicitly asks for mail, newsletters, or promotions. Human correspondence and important temporal candidates retain normal retrieval eligibility, subject to the global context caps.

External fact extraction fails closed twice: `gmail_thread` is disabled by default and requires an explicit source-type opt-in, and every opted-in document must still have `fact_eligible: true`. The production personal-Brain configuration leaves that opt-in disabled, so Gmail projections are indexed and recalled locally without sending their contents to the external extractor. Absence of an automation marker is not human evidence. Human admission requires at least 40 retained body characters within the message ranges admitted to extraction, plus a positive signal such as Gmail `CATEGORY_PERSONAL`, Gmail `SENT`, or an operator-authored/reciprocal thread. A bulk or advertising message in the same thread is excluded from those ranges but does not suppress an independently qualifying human message. Unclassified legacy mail remains indexed as `unknown` but is not fact-eligible.

Transactional mail has a separate, narrow temporal lane. One individual message must have an event/obligation signal in its subject and a nearby explicit date/time in that same message, and the qualifying admitted message bodies must retain at least 120 characters. Event subjects include meetings, interviews, appointments, reservations, bookings, travel, sessions, and deadlines. Financial obligations also require explicit action language. Package delivery estimates, passive auto-pay dates, body-only newsletter mentions, bulk/list mail, and advertising do not qualify. The connector persists the admitted message IDs, validates them against the trusted timestamp/range index, and gives extraction only chunks overlapping those message ranges; one qualifying message cannot expose every routine update in a long thread. Body-sufficiency gates are measured only over those admitted message bodies, never over unrelated retained messages in the thread. This gate only permits model inspection; the extractor and critic must still support any fact and event from cited evidence.

The classifier version, provider-label availability, human-signal basis, delivery kind, importance, actionability, and admission basis are persisted in frontmatter for aggregate audit. Projection v7 also persists an ordered per-message policy row bound to the trusted message timestamp/range index. Each row records message-local delivery, strong provider-promotion and weak lexical-advertising bases, exact fact-admission basis, provider important/star state, positive human evidence, and whether an operator-authored message occurs later in the same thread. The policy must reconcile exactly with admitted message IDs and aggregate delivery before capture, activation, extraction, or temporal review trusts it. A promotion in one message therefore cannot suppress a separate interview or human reply. Lexical advertising alone is review evidence rather than an unconditional negative; provider promotion remains a hard negative unless explicitly starred. Non-ad bulk/list temporal mail requires target-specific relevance before entering rescue. New archive writes retain Gmail labels. Historical archive rows created before that field was persisted report the coverage gap explicitly and rely only on RFC headers plus operator-authored direction; they never default to human.

### External-model and secret boundary

Email headers and bodies are untrusted external data. Extractor, critic, auditor, direct MCP, proxy MCP, and generic Brain retrieval consumers are instructed never to follow embedded commands, links, policy claims, disclosure requests, or assertions that an attachment was read. Generic fact-only and page-only responses resolve source provenance before deciding whether to attach the Gmail untrusted-content warning. Sending normalized mail to an external extraction or audit model is a separate privacy boundary from archive synchronization and requires the explicitly configured Brain v2 model path. All external Codex one-shot invocations MUST use ephemeral execution so the CLI does not persist a session transcript. Ephemeral execution prevents new local session-history persistence; it does not make private message content non-sensitive or remove the external-processing boundary.

Before any model request or model-derived output boundary, the Gmail path applies an offset-preserving sanitizer for credentials, one-time codes, passcodes, meeting and booking locators, authentication/signed links, private-key material, and exact sensitive values recognized from the admitted evidence. Labeled codes are recognized in prefix, postfix, action, account, OTP, and verification-number forms; authentication-scoped path, query, and fragment tokens are masked without treating ordinary years, budget codes, help URLs, or non-secret slugs as credentials. The same boundary covers initial and retry extraction prompts, critic context and repair, audit cards, cached evidence quotes, every textual MCP field, and Gmail-specific outputs. Sanitized quotes MUST preserve source offsets so validation continues against the trusted rendered range. A candidate whose predicate is the sensitive value itself MUST be rejected, not stored in redacted form. Pattern masking is defense in depth; logs, errors, reports, tests, and repository documentation MUST remain content-free and MUST NOT claim that arbitrary private prose is safe.

### Claim quality and scope

Source admission only authorizes inspection. Gmail facts still pass deterministic claim-quality gates before model judgment and application:

- a request is not a commitment, a conditional scheduling instruction is not an agreed schedule, and an unanswered question is not a durable fact;
- routine access details, booking attributes, credentials, and delivery mechanics are not durable knowledge;
- a context-specific statement cannot be generalized into a universal rule;
- normative claims retain their source and authority scope, including any carrier, provider, organization, policy, project, or named situation on which they depend;
- the target person page must be identity-compatible with the cited source, with stricter rejection for health or medical claims;
- only the core event identity, supported schedule, direct obligation, durable decision, or durable relationship/context may survive the Gmail source policy.

These checks run again at application time. A later prompt or critic regression therefore cannot bypass the source claim, identity, or privacy boundary.

### Event routing and temporal repair

The connector emits a versioned, provider-authored index of message ID, Gmail internal timestamp, and exact rendered byte range. Brain validates the immutable source/raw path, content hash, account/thread/message lineage, timestamp, and cited span before assigning `observed_at`; sender-controlled headings and `Date` headers are never trusted clocks. Thread creation/update, archive sync, ingestion, and model-processing time are never assertion time. A schedule or deadline may receive planned event time only when the cited text supports a named event; message arrival never proves occurrence.

Every Gmail fact targeting an `events/` page requires one grounded occurrence compatible with that page, even when the candidate's primary entity type is person, place, organization, or product. In this tranche, routing may consume only a structured `event_time` that survived the cited temporal-repair boundary. The precheck can identify a potentially compatible applied same-source occurrence for review, but that anchor is not apply-eligible until it has its own replayable provenance contract. A model-proposed dated path, an existing event page's own date, an unaccepted/rejected/held sibling, adjacent legacy date intervals, or looser regexes over a model-authored statement MUST NOT lend occurrence identity. Ambiguous, conflicting, cross-occurrence, or unresolved routing becomes L3 review. The same event-identity guard is repeated when an action is applied, and half-open end bounds cannot overlap an event beginning at the exclusive end.

Temporal discovery is now evidence-first and sidecar-only. It operates independently inside each trusted Gmail message range and returns normalized candidate bounds, relation, kind, precision, exact half-open source offsets, and an explicit `resolution_basis`; it does not emit raw source text, route a page, or persist a fact. Supported discovery includes explicit textual and ISO dates, conservative textual ranges, source-clock-bounded month/day and relative expressions, and clocks with explicit numeric offsets, UTC/GMT, IANA zones, or explicitly identified fixed North American abbreviations. Missing or ambiguous timezones, ambiguous meridiem, and DST folds/gaps degrade to day precision. Inferred-year, relative, abbreviation-based, unzoned, multi-event, lifecycle, and classifier-assisted associations remain review-only.

The existing narrow temporal stabilizer still owns route-eligible Gmail time. Once cited evidence and a named primary event survive stabilization, Brain writes an evidence-bound integrity checksum over the statement, event, normalized clock, exact chunks/spans, and complete stabilizer audit. The checksum detects ordinary mutation but is not treated as an authentication secret. Application reloads the cited SQLite chunks, resolves Gmail origin independently of candidate metadata, reruns stabilization, and requires the clock, primary event, and complete replay audit to match. A document-only citation cannot supply a Gmail clock because apply-time replay requires exact chunk spans. Nested/flat conflicts, altered or stale checksums/audits, unsupported model-authored dates, and Gmail flat-only event fields fail closed. Non-Gmail manual facts retain their existing behavior.

The content-safe historical evaluator validates the connector-authored message timestamp/range index before discovery, removes the connector-added timestamp heading from candidate evidence, replays current state and immutable history deterministically, and emits aggregates plus optional HMAC-opaque sample identifiers only. It never writes Brain state. On the full projection it processed all 42,533 files, collapsed 28,306 renderer/classifier variants into 14,227 source revisions, and exactly reproduced 6,960 active threads, 165 deleted threads, and 356 fact-eligible threads. The 5.11% fact-admission rate is within 0.31 percentage points of the original Brain's 4.8% benchmark.

The 2026-07-22 isolated v7 rebuild supersedes that renderer for current authority without deleting the historical evidence. Capture and ingest completed 7,125 revisions and 16,118 chunks with zero errors. The authoritative aggregate-only runner prepared 7,857 of 7,859 active messages: 733 entered the original fact lane, 2,338 entered temporal rescue, and 4,786 were not admitted. The fact-lane population remained exactly 733 across the v6-to-v7 change. After recovering exact endpoints that share an expression's deterministic sentence segment even when the bounded prose window is trimmed, it produced 2,123 candidate-bearing messages, 34,584 legal candidates, and 13,548 bounded pages; only two messages failed with explicit batch omissions and no candidate frontier failed. Both failures were non-advertising, non-fact-admitted, relevance-free rescue messages, so fact-admitted structural completeness was 100%. Compared with the last pre-v7 diagnostic, candidate-bearing coverage rose from 1,982 and failures fell from 88. Overall page volume is 1.72 per mailbox message; candidate-bearing p95 is 22 for historical backfill. This is structural recall and completeness evidence only. No private message was sent to a model, and semantic precision/recall remain unmeasured until the frozen private holdout is independently labeled and explicitly authorized for the pinned verifier.

Message-level temporal review v3 keeps model-selected subject mentions as exact evidence and carries deterministic event identity separately. A hypothesis may expose its complete source-proven subject alias family plus one canonical title only when the family contains exactly one event-title candidate and the selected subject is event-centered. Ambiguous families and non-event actions have no canonical title. Event-identity units bind the same split, and a transient source-bound consumer resolves mention IDs back to checked source spans for bounded pair requests and post-resolution retrieval bindings. Retrieval receives qualified canonical titles only; generic heads such as `meeting`, `review`, and `session` are never exported as aliases. These additions improve named-event recall without treating deterministic aliases as retroactive model support, and all outputs remain deferred and non-routable.

The public-synthetic challenge protocol freezes current V4 gold before predictions and scores temporal semantics, named-event identity, and verifier calibration as separate axes. The V3 freezer accepts as many as 128 cases and retains positive cases even when the deterministic frontier produces no verifier request or omits a gold member; frontier-covered, frontier-missing, positive-zero-work, and candidate-bearing positive/negative counts are written as a content-free owner-only HMAC sidecar bound to the exact fixture, challenge manifest, gold, and challenge ID. The signed challenge and gold schemas remain unchanged. The prediction `run` phase accepts and reads neither gold nor this sidecar. Score v13 may validate the sidecar and bind its exact SHA-256 and aggregates into the signed score, while omission remains allowed for historical frozen challenges; a supplied invalid or stale sidecar fails closed. An optional `--gold-audit-root` must contain the exact approved fixture copy, authenticated plan, detail, and summary, plus every bounded request, response, and signed receipt. The scorer pins the fixture-generator version and source SHA-256, audit contract, external `gpt-5.6-sol` model, medium reasoning, and restricted ephemeral execution; it replays exact case/order coverage, aggregate counts, artifact hashes, and plan-to-call-to-detail-to-summary chronology, requires completion before the prediction plan, and accepts only zero corrections. Missing, extra, tampered, stale, post-plan, local, or test evidence fails closed. Historical scores may omit the audit root, but their personal target gate is explicitly unavailable rather than silently satisfied.

Prediction-blind Sol-medium source labels require complete coverage and a separate owner audit over a fixed HMAC quarter plus every error in each cohort. Sparse or selectively omitted labels cannot satisfy a gate. ## Encrypted Gmail History Archive

The archive is a separate local evidence store, not a wider operational mirror or a Knowledge-ingestion path. It uses the account-bound Gmail API to save the exact RFC-2822 bytes returned by `messages.get(format=RAW)`, including MIME attachments. Raw messages and the parsed text used for local search are encrypted with AES-256-GCM; the archive key is held in macOS Keychain.

V1 has one sync state machine. It performs a resumable fixed 90-day backfill, then follows Gmail history incrementally for new and changed messages. If the Gmail history cursor expires, it restarts the full scan safely. A provider deletion marks the message unavailable at Gmail but retains the local ciphertext.

V1 search is intentionally simple: the daemon decrypts and scans locally when requested, then returns bounded results. It does not maintain a second full-text, token, or embedding index. `search_mail` returns bounded metadata and snippets; `get_mail_thread` returns bounded parsed text and attachment descriptors, never attachment bytes. Both tools require the authenticated daemon, are absent from the direct MCP fallback, and label message content as untrusted.

The scheduler reports the stored-message count, current state, or a plain-language pause reason; Gmail's unreliable result-size estimate is not presented as a total. Managed storage reports archive file size. Archive sync never mutates Gmail and does not invoke Luna, another LLM, fact extraction, Knowledge Curation, or the operational detector.

The first private run copied the fixed window from 2026-04-15T23:42:21Z through 2026-07-14T23:42:21Z, then processed five Gmail history changes and reported current. The result contains 7,746 active messages across 6,857 threads: 758,041,932 original raw bytes in an encrypted SQLite file occupying about 403 MB at installed verification. SQLite `quick_check` is `ok`; the store has exactly the three application tables defined by V1, its directory/database permissions are `0700`/`0600`, the archive is bound to the approved immutable Gmail identity, and the Keychain value round-trips as a 32-byte key.

The app and daemon surface is defined in [App And Operations](specs/app-and-operations.md).
